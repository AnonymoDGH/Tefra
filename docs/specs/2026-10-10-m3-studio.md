# M3: Tefra Studio, un motor para hacer juegos completos

Fecha: 2026-10-10. Estado: en curso.

Petición del usuario: "quiero algo más profesional, voy a crear juegos con esto: programar con C#, una GUI similar a Roblox Studio, un MCP para la IA y opciones reales para juegos completos (animaciones de personajes, avatares, etc.)".

Este hito convierte el motor de render (M0–M2) en una herramienta de creación de juegos. M2 (look) queda pausado: lo que ya existe (terreno, océano, vegetación, atmósfera) se expone en Studio como servicios.

## 1. Experiencia objetivo

1. Abrir `tefra_studio`. Aparece una disposición tipo Roblox Studio:
   - Explorer (árbol de instancias) a la derecha arriba.
   - Properties debajo.
   - Viewport 3D en el centro.
   - Toolbox / Insertar.
   - Output (logs y errores de scripts) abajo.
   - Barra de herramientas: Select, Move, Rotate, Scale, Play, Pause, Stop.
2. Insertar Parts, modelos glTF, luces, un SpawnLocation y Scripts. Moverlos con gizmos y editar propiedades.
3. Escribir lógica en C# (`Script` con código fuente). Con Play se compila (Roslyn) y se ejecuta. El personaje (avatar R15) aparece en el SpawnLocation y se mueve con WASD, salta y anima. Stop vuelve al estado de edición.
4. Guardar y abrir el lugar (`.tefra`, JSON legible y diffeable).
5. Una IA (Claude Code u otra) se conecta al MCP de Studio. Puede leer el árbol, crear y editar instancias, escribir scripts, darle a Play o Stop, leer el Output y capturar el viewport.

## 2. Decisiones (ADRs nuevos; sustituyen a ADR-007)

### ADR-011: Editor Tefra Studio
- Dear ImGui (rama docking, MIT, vendored) con backends GLFW y Vulkan. Gizmos con ImGuizmo (MIT).
- El viewport es el render diferido del motor a un offscreen que se muestra como imagen ImGui. Cada panel es un módulo independiente.

### ADR-012: DataModel (árbol de instancias)
- Al estilo Roblox: `game` (DataModel) → servicios (Workspace, Lighting, ReplicatedStorage, ServerScriptService, StarterPlayer) → instancias.
- Cada clase registra sus propiedades tipadas: bool, int, float, string, Vector3, Color3, enum y referencia a instancia. Las propiedades se leen y escriben por nombre. La reflexión es la misma para el editor, la serialización, C# y el MCP: una sola fuente de verdad.
- Sin RTTI ni excepciones (ADR-002): `ClassInfo*` hace de tipo, y `IsA` recorre la herencia.
- Serialización JSON `.tefra`. Los ids estables (u64) permiten las referencias.

### ADR-013: Scripting C# (.NET 8)
- El host nativo carga el runtime con `hostfxr` (API C de .NET; funciona con MinGW).
- `Tefra.Engine.dll` (C#) expone la API: `Instance`, `Part`, `Vector3`, `Workspace`, `Input`, `RunService`, eventos.
- Los scripts de usuario se compilan en memoria con Roslyn y se cargan en un `AssemblyLoadContext` coleccionable, lo que permite recargar al pulsar Play.
- Interop: tabla de punteros a funciones nativas en `[UnmanagedCallersOnly]` (ida) y callbacks de eventos (vuelta). Nada de reflexión en caliente.
- Requisito en el PC del usuario: .NET 8 SDK. Si falta, Studio arranca igual sin scripting y lo avisa.
- Excepción documentada a ADR-002: el lado gestionado (C#) usa excepciones. Nunca cruzan la frontera: el host las captura y las manda al Output.

### ADR-014: Física con Jolt Physics (MIT, vendored)
- Parts: estáticos si están anclados (`Anchored`), dinámicos si no.
- Personaje con `CharacterVirtual`.
- Raycasts para la selección del editor y para los scripts.

### ADR-015: MCP integrado
- Studio sirve MCP (JSON-RPC 2.0, transporte Streamable HTTP) en `http://127.0.0.1:44755/mcp`.
- `tefra_mcp` hace de puente stdio↔HTTP para los clientes que solo hablan stdio.
- Herramientas: árbol, propiedades, crear, borrar, mover instancias, leer y escribir scripts, Play/Stop, Output y captura del viewport (PNG en base64).
- Solo escucha en localhost.

### ADR-016: Animación y avatares
- Animación esquelética: skins y clips de glTF (cgltf), skinning en GPU (paleta de joints vía BDA), mezcla y crossfade, y una máquina de estados simple (idle, walk, run, jump, fall).
- Avatar por defecto estilo R15: 15 piezas unidas por articulaciones (`Motor6D`) con animaciones keyframe propias (procedurales, sin licencias). También se pueden importar personajes glTF con rig.
- `Humanoid` controla la vida, la velocidad, el salto y el estado.

### ADR-017: Importador de lugares de Roblox (excepción autorizada por el usuario)
- El brief prohíbe lectores de formatos de juegos comerciales. El usuario pidió de forma explícita importar **sus propios** lugares (`.rbxl` binario, `.rbxlx` XML) para migrarlos a Tefra. Esta es la única excepción.
- Se implementa clean-room, solo desde documentación pública del formato (la especificación de rbx-dom/rojo, MIT). No se copia código de Roblox ni de terceros. Los descompresores (LZ4, zstd) son bibliotecas permisivas vendored.
- No se descarga nada de Roblox: las referencias `rbxassetid://` se conservan como texto y no se resuelven. El repo no incluye ningún archivo de Roblox; los tests construyen sus muestras en código.
- Conversión: 1 stud = 0,28 m. Se convierten las clases equivalentes (Part, WedgePart, SpawnLocation, Model, Folder, luces, Sound, GUI y scripts). Las demás quedan como `ImportedInstance` (OriginalClass + OriginalProperties). El Luau se guarda en `LuauSource` y el script se importa desactivado, con una plantilla C# comentada.

### ADR-018: Runtime compartido y exportación
- `engine/runtime` (GameRuntime) ejecuta el juego igual en Studio y en `tefra_player`.
- Exportar = carpeta autocontenida: `tefra_player(.exe)`, `shaders/`, `managed/` (si hay scripts), `game.tefra`, los assets referenciados y `game.json` (título, ventana).
- El sonido usa miniaudio (MIT-0/Unlicense). La UI del juego se dibuja con listas de dibujo de Dear ImGui.

## 3. Módulos

| Módulo | Ruta | Contenido |
|---|---|---|
| core | `engine/core` | + `JsonValue` (DOM, parse y dump) |
| world | `engine/world` | DataModel, Instance, reflexión, clases base, serialización, puente al renderer |
| physics | `engine/physics` | Jolt, cuerpos sincronizados con los BaseParts, personaje |
| anim | `engine/anim` | esqueletos, clips, Animator, rig R15 y sus animaciones |
| scripting | `engine/scripting` + `managed/` | host .NET, interop, `Tefra.Engine` (C#) |
| mcp | `engine/mcp` | servidor HTTP mínimo, JSON-RPC, herramientas MCP |
| studio | `apps/studio` | ImGui, paneles, gizmos, modo Play |

## 4. Plan por fases

| Fase | Contenido |

| F1 | JSON DOM, DataModel con reflexión, clases base, `.tefra`, render de Parts (en curso) |
| F2 | Studio: ventana, docking, Explorer, Properties, viewport, gizmos, selección, Play/Stop |
| F3 | C#: host, API, ciclo de vida de los scripts, Output |
| F4 | MCP |
| F5 | Física + personaje + avatar R15 animado + SpawnLocation |
| F6 | glTF con skin, Animator con mezcla, importación de personajes |
| F7 | Plantillas (Baseplate, Playa, Valle), publicación de un juego como ejecutable standalone |

F2–F6 avanzan en paralelo sobre la API de F1.

## 5. Criterios de "hecho" de M3

- Un juego de ejemplo ("Obby" de plataformas con checkpoints) hecho solo con Studio y C#, que se puede jugar.
- Validación Vulkan con 0 errores. CI verde en Linux y Windows.
- Claude Code conectado por MCP puede construir un nivel y ejecutarlo.
